P14 (pinned this round, owner-approved personal-data prefill; R7-01 implements core, siblings code against it and import lazily/fail closed): (1) Runner profile = {full_name, given_name, family_name, email, phone, birth_date (ISO), gender, nationality (ISO-3166 alpha-2), address_line, postal_code, city, country}; all optional strings. It lives ONLY in process memory on the mission (never in Mission JSON responses, events, logs, evidence, replay fixtures or disk); the API exposes only `profile_status: {complete: bool, fields: [field names present]}`. (2) `POST /api/missions/{id}/profile` with that object (pydantic, length-capped, email/phone/date validated) returns the Mission (profile_status only). DELETE clears it. Allowed in guiding/ready states only. (3) At confirm, the LiveRunner passes the profile to builders as `trip['runner_profile']` (dict, may be absent). Builders MUST NOT copy values into `instructions` text; they set `task['prefill_fields']=[field names the site form needs]` and `task['prefill_scope']` (short description e.g. 'participant form', 'guest details', 'passenger details'). hclient appends, only in the prompt sent to H, a block 'Runner profile (type only into the {prefill_scope} fields; never submit a final form)' containing exactly the prefill_fields values, and scrubs every profile value (and case-folded variants) from steps, answers, summaries, handoff URLs and logs before anything leaves hclient. (4) Guardrails: typing profile values into participant/guest/passenger fields is ALLOWED when prefill_fields is non-empty; pressing an intermediate 'Continue/Next' that only moves to the next form page is allowed; still NEVER pay, create an account/log in, accept terms/medical/consent checkboxes, solve captchas, or press a final submit/confirm/book/pay button. `_payment_claim` keeps rejecting payment/booking/form_submitted(final)/account_created/terms_accepted; `personal_data_entered=true` is accepted only when the task had prefill_fields. (5) Checkpoint semantics: a task may carry `checkpoint['prefill_patterns']` (pages where fields are typed, do NOT force_answer there) in addition to url_patterns (final pre-payment stop) and beyond_patterns. Without a profile, behaviour is exactly as today (stop at first personal-data page untouched). (6) StepResult gains optional `prefilled: bool` and `stop_label` (short friendly FR/EN-neutral string such as 'payment page reached'); never contains values.
